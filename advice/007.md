### 1.2 ⚠️ C1 的 derivative 检查仍是恒真式（005 §四 未完全闭环）

`run_mvsc01.py`：
```python
def g_right_deriv(self, b):
    return float(self.probs[self.vals > b].sum())   # 实现即 P(Y>b)
# 测试：
abs(pmf.g_right_deriv(b) - float(pmf.probs[pmf.vals > b].sum())) < 1e-12
```
这是 `P(Y>b) == P(Y>b)`，**恒真、永不可能失败**。上一轮只统一了 A/B/C
命名（005 §四），没有按 005 建议把验证强度提升到 `phase_boundary.py` 的
独立路径（g_from_support vs g_alt + tower property）。报告声称 "∂⁺g=survival
成立 → PASS" 名不副实。

**建议**：T29 已有真实支持（exact support 的 survival 对照），C1 应改为
引用/复用 `phase_boundary.verify_identity`，或至少把测试改成用独立实现的
数值导数（如中心差分）对照，而不是实现与测试共用同一表达式。

### 1.3 ⚠️ `static_prog_decision` 在 QoS-dual 停止规则下大量退化

复算：StaticProg 在 **23/28** 的 (ρ,η) 网格点 E[B]=0（root 处 R≤min Q 立即
STOP，什么都不发）。原因：QoS-dual 停止规则 `R(x) ≤ min_a Q^(1)` 在 root
（R=ρ·min{p,e^η(1−p)}）恒小于单步 Q（≈ρ 量级 + 17），所以固定顺序 ladder
在大多数乘子下根本不启动。

这与 005 §八 的 "Static Progressive 主基线" 意图有偏差：baselines.py 的
B11 用 `|Ω|≥η_s` 停止且强制渐进，而这里复用的 QoS-dual 停止导致退化。
**不一定是 bug**（StaticProg 作为 QoS-dual 族一员达不到 QoS 是真实结论），
但报告 §4 只说 "∅ 无 FEASIBLE"，未说明 23/28 是全停退化点，读者可能误以为
是"渐进但不够快"。

**建议**：§4 补一句 "23/28 网格点为 E[B]=0 全停退化（QoS-dual 停止在 root
即触发），仅 5 个点有实际发送行为"。

## 二、数据问题

### 2.1 ⚠️ convex-hull 诊断用点估计，与正式 U95 口径不一致

`convex_hull_diag` 用 `kfa/n0`（点估计）判断是否进入 QoS 象限，而
`classify_qos` 用 **Wilson U95 上界**。复算：StaticProg 的 9/378 对
"2-point mixture 进入 QoS 象限" 全部来自点估计口径；用 U95 上界（保守
max 近似）则 **0/378**。005 §六 的 convex-hull 论点在**期望值**上成立
（error prob 对 mixture 线性），但统计认证必须用 U95——报告 §5 未说明
口径差异，9 对"进入"会误导读者以为 policy-class 可行。

**建议**：报告 §5 注明 "点估计口径（期望值线性）；正式认证需 Wilson U95，
U95 口径下进入数可能为 0"，或直接改为 U95 判断。

## 三、文档问题

### 3.1 🔴 A 区不可达的论证错误（结论对、理由错）

`run_mvsc03a.py` 报告代码（及两份报告、advice/006.md 共 4 处）写：

> "其余 3 UAV 最多花 3×20=60 < 76−79，数学上不可达"

**前提错误**：单 UAV 可渐进 ladder 0→1→2→4 = 17+17+18 = **52**，3 UAV 最多
可花到 156，并非 60。A 区（花费 ∈(76,79]，即剩余 h∈[17,20)）确实不可达，
但正确理由是：**4-bit ladder 下 3-UAV 可达花费集合 {51..58,60,68..74,76,85..}**
中 (76,79] 内无值（74→76 间隙 2、76→85 间隙 9；76 对应 h=20 是 B/C 边界）。

**建议**：改为 "枚举 3-UAV 可达花费（单 UAV ∈{17,18,20,34,36,52}），
(76,79] 内无可达值 ⇒ A 区不可达"。

### 3.2 🔴 等价性审计规模声称不一致（300 vs 40）

README（621 行）、`run_mvsc03a.py` docstring（12 行）、C3a 报告头部、
advice/006.md 均写 "300 episodes × 3 corners × H∈{48,96}"，但 T40 回归实际
用 **40 episodes**（`rng8.integers(0,2,40)`）。开发期确实做过 300-episode
审计（临时脚本，未保留），T40 是 40-episode 轻量回归——两者都真实，但文档
把 300 的声称挂在 T40 名下，读者会以为 T40 就是 300。

**建议**：T40 提到 40（或补到 300），文档统一。

### 3.3 ⚠️ runtime 声称互相矛盾

README 三处：C2.1 bullet "757.6s"、C2.1a bullet "642.1s"、C2.1b bullet
"739.2s"；当前 C2.1 FULL 报告实际 "665.6s"。四值并存且都是同一 runner 的
不同运行（墙钟），文档未说明"墙钟可变、以报告为准"。

**建议**：只保留最新值（665.6s）或注明各为不同运行的墙钟记录。
